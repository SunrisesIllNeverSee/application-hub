Notes on the environment:

- All servers ran locally with a placeholder Supabase project (`https://acceptance0ref.supabase.co`, dummy anon key, no service-role key). The dev and production servers sent every server-side outbound request to `tests/acceptance/deny-proxy.mjs`, which records the host and refuses it. The browser aborted every request that left localhost. Hosts the servers tried and were refused: `registry.npmjs.org` and `fonts.googleapis.com` (next dev / next/font tooling) and `acceptance0ref.supabase.co` (middleware `auth.getUser()` for the synthetic AT21 cookie); the production server made none. The browser's only off-site attempt was the root layout's GA4 script (`GET /gtag/js`, no body).
- `db` and `catalog-sql` use throwaway Postgres clusters (initdb in the scratch dir, loopback only) with the production migration order (`supabase/tests/m09/run_local.sh`). Nothing connects to Supabase.
- AT19 runs a real headless Claude Code session (`claude -p … --mcp-config … --strict-mcp-config --allowedTools "mcp__aqua__*" --tools ""`) from a scratch dir holding only the `npm pack`ed companion. Without `--agent` the runner re-checks the recorded outcome in `m09-acceptance/at19/outcome.json`.
- **Real sign-in is not part of this run.** The synthetic production accounts' passwords are unknown and recovering one would be a production auth write, so the real-login run is deferred to the post-merge production check. AT21 uses a synthetic auth cookie (what `@supabase/ssr` writes; in the client it is only a vault-routing hint) and supabase-js's own BroadcastChannel sign-in/sign-out events.
- **CI could not have run on the pre-fix integration branch.** `m09/integration` carried committed merge-conflict markers in `.github/workflows/ci.yml` (next-app job) until `2880d0c`, so GitHub could not parse the workflow and no CI result exists for those commits. This branch includes the fix (and its markers guard); the results here come from local runs.
